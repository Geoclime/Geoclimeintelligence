# Database Layer: Entities, Repositories & Migrations

## What was built

The way the backend stores and reads data in PostgreSQL. **Entities** describe each table in TypeScript. **Repositories** are the only code allowed to query the database. **Migrations** are numbered scripts that create or change tables in a controlled, repeatable order. Phase 1 created the first two tables: `roles` and `users`.

## How it works

All paths are relative to `server/`.

**1. The connection.** [`src/config/data-source.ts`](../server/src/config/data-source.ts) creates the one `AppDataSource`, TypeORM's connection to PostgreSQL. It lists the entities and where the migrations are, and sets `synchronize: false`. TypeORM can alter tables automatically to match the code, but that can silently drop data, so here the schema only ever changes through migrations. SSL settings are explained in [database-connection-ssl.md](database-connection-ssl.md). Only repositories, the migration tool and admin scripts may import `AppDataSource`; controllers and services never do.

**2. Entities describe tables.** [`src/modules/users/user.entity.ts`](../server/src/modules/users/user.entity.ts) and [`role.entity.ts`](../server/src/modules/users/role.entity.ts) are classes with **decorators** (the `@Entity`, `@Column` lines) that map TypeScript properties to columns:

```ts
@Column({ name: "firebase_uid", type: "varchar", length: 128, unique: true })
firebaseUid!: string;
```

The database uses `snake_case` column names (`firebase_uid`) and the code uses `camelCase` (`firebaseUid`); `name:` connects the two. Every column states its `type` explicitly because `tsx` doesn't provide the type information TypeORM would otherwise guess from.

**3. Repositories are the only door to the data.** [`src/common/repository/base.repository.ts`](../server/src/common/repository/base.repository.ts) gives every repository `findById`, `findPage` (offset pages) and `findCursorPage` (cursor pages; see [pagination.md](pagination.md)). [`src/modules/users/user.repository.ts`](../server/src/modules/users/user.repository.ts) extends it with user-specific queries:
- `findByFirebaseUid` is used on every request to match a Firebase login to our row.
- `findByEmail` compares case-insensitively (`lower(email)`), so `Ada@x.com` and `ada@x.com` are the same person. The `idx_users_email_lower` index keeps that fast.
- `createIfAbsent` handles a real race. A new user's app often fires several requests at once, and each would try to create the same row. The insert uses `ON CONFLICT DO NOTHING` (TypeORM's `.orIgnore()`), so one insert wins, the others do nothing, and all of them then read back the same row. Nobody gets an error.
- `updateAccess` changes a user's role and scope.

The base repository fetches TypeORM's repository object lazily, when first used, because TypeORM only knows about entities after the database connection is initialised.

**4. Migrations change the database.** [`src/migrations/1790600000000-CreateRolesAndUsers.ts`](../server/src/migrations/1790600000000-CreateRolesAndUsers.ts) is the first one. Its `up()` does four things:
- Creates `roles` and fills in the five roles. These are reference labels from the standard, not observed data.
- Creates `users`. It has **no password column**, because Firebase holds passwords. It has these constraints:
  - `uq_users_firebase_uid`: one row per Firebase account.
  - `fk_users_role`: `role` must be a real code in `roles`. A role in use can't be deleted, and renaming a role code updates users automatically.
  - `ck_users_scope_only_for_staff`: only responders and officials may have a region scope.
- Gives `id` a random UUID generated by the database (`gen_random_uuid()`, built into PostgreSQL 13+).
- Adds the case-insensitive email index.

`down()` undoes it by dropping both tables.

TypeORM records which migrations have run in its own `migrations` table. The commands are:

```bash
npm run migration:show     # [X] = applied, [ ] = pending
npm run migration:run      # apply all pending, in timestamp order
npm run migration:revert   # undo the most recent one
```

**The golden rule:** never edit a migration that has already run anywhere, whether on your machine, staging or production. Its changes are already in those databases and editing the file won't re-run it. Add a new migration instead. The number in the file name (`1790600000000`) is a timestamp that fixes the order.

**What happened on 2026-09-28:** this migration was run against the team's Aiven PostgreSQL database, and `migration:show` now lists it as applied.

**Coming next (Phase 2):** the first migration that needs geometry will enable the PostGIS extension. It will also add the `users.scope_admin_unit_id → admin_units.id` foreign key. Every geometry column will get a GiST spatial index (standard section 8).

## Explain it like I'm new to this

The database is a big filing room. An **entity** is the printed layout of one kind of card, for example a user card: which boxes it has and what goes in each. The **repository** is the archivist, the only person allowed in the filing room. Everyone else asks the archivist ("find the user with this Firebase ID") instead of rummaging through cabinets themselves, which keeps the room tidy and every search done properly. A **migration** is a numbered renovation order for the room: "Order 1: install a roles cabinet and a users cabinet, with these locks". The room keeps a list of which orders it has carried out, so running the orders again only does the new ones. You never rewrite an order that's already been carried out; if you want a change, you issue a new order.
